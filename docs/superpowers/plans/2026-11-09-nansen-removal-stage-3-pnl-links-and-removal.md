# Nansen removal, stage 3: PnL, funding links, the client's removal and attribution - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** No Nansen call anywhere in the code path of a new check: 30-day PnL comes from Hyperliquid's `portfolio`, the funding links (which wallets first funded the account) come from a block explorer, the Nansen client and its credit meter are gone, and every share, embed and picture credits exactly the sources a reading used.

**Architecture:** Two new read sources replace the three Nansen reads that stage 2 left (PnL, funding links on two chains, funding history for longs): `getPortfolio` (Hyperliquid info, one request) and `src/sources/explorer.ts` (Blockscout, one request per chain and a third for the label of an Arbitrum sender, an API key optional). The funder search in `observe.ts` keeps its structure and rules and changes only where links come from. Attribution moves into one server-side function whose strings the browser scripts display.

**Tech Stack:** TypeScript, Cloudflare Workers (Free plan), Vitest, Blockscout REST API v2.

**Spec:** `docs/superpowers/specs/2026-10-20-redesign-and-nansen-removal-design.md`. Earlier stages: `docs/superpowers/plans/2026-10-20-nansen-removal-stage-1-all-dex-positions.md`, `docs/superpowers/plans/2026-11-09-nansen-removal-stage-2-request-budget-and-holdings.md` (its "Left for stage 3" list and Execution record (d) are this plan's backlog). Local migration plan: `docs/internal/NANSEN_REMOVAL_PLAN_2026-10-14.md` (git-excluded).

## Global Constraints

- No production deploy and no merge to `main` before the Colosseum results (expected 11-21.11.2026); work stays on `remove-nansen`. No Worker is run for testing; no Nansen request is sent by any test, script or smoke.
- Public repository: English only; plain hyphen `-`, never the long dash, in code, comments, docs, commit messages.
- Verdict rules (`computeVerdict`, 22 reason codes) do not change; every golden snapshot difference is read field by field and explained in the Execution record. The bet rule is never loosened to compensate for a source that could not be read: an unread source lowers coverage and the verdict is withheld.
- The check's own request budget stays 45 (`CHECK_REQUEST_LIMIT`); the heaviest tested check must stay at most 42 requests: 29 Hyperliquid + 1 `portfolio` + 3 explorer (Ethereum, Arbitrum, and the label of the Arbitrum sender) + 9 node reads (it was 41 with 2 explorer reads until the first live run with a key, 2026-11-10; Execution record (a), (c)). A larger registry or an extra retry must still be stopped by the budget.
- Hyperliquid's `portfolio` response (live 2026-11-09): an array of `[period, { accountValueHistory, pnlHistory, vlm }]` for `day, week, month, allTime, perpDay, perpWeek, perpMonth, perpAllTime`; each history is `[timestampMs, "decimalString"]` and `pnlHistory` is cumulative from the period's start (Abraxas `perpMonth`: first `"0.0"`, last `"85200826.2125139982"`, 49 points). The 30-day figure is last minus first of `perpMonth.pnlHistory`.
- Blockscout (read 2026-11-09): the public per-chain hosts "sit behind bot protection" and scripted requests "can receive a `403` response whose body is an HTML 'Just a moment...' challenge page"; "per-instance API support has been deprecated" in favour of the universal API at `https://api.blockscout.com`, key as `Authorization: Bearer <key>` (also `apikey` query parameter, not used here), REST path `https://api.blockscout.com/{chain_id}/api/v2/addresses/{address}/transactions` with `filter=to`, `sort=block_number`, `order=asc`. Free tier: "100K credits/day · 5 RPS · All chains", 20 credits per call (about 5,000 calls a day), 429 over the RPS limit. No terms page for the PRO API on display, storage or attribution could be found (https://dev.blockscout.com is a script-only page, its `/terms` is a 404); the owner reads the terms at sign-up (Prerequisites). Keyless `https://eth.blockscout.com/api/v2/addresses/<address>/transactions?filter=to&sort=block_number&order=asc` answered 200 from the dev machine on 2026-11-09 (Abraxas: first inbound transaction from `0xed0c6079229e2d407672a117c22b62064f4a4312`, 2025-07-08, 0.02 ETH; this is the funder the September Nansen fixture also named); `https://arbitrum.blockscout.com` answered 403 with the challenge page. First live run with a key (2026-11-10, Execution record (a)): the REST path above is right for Ethereum only; on Arbitrum it answers 500 to `sort=block_number`, so Arbitrum is read through the Etherscan-style `https://api.blockscout.com/v2/api?chain_id=42161&module=account&action=txlist&address={address}&sort=asc&page=1&offset=50`.
- First-funder rule (Nansen's "First Funder" parity): the sender of the earliest inbound native-coin transaction with value above zero to the address, on Ethereum and on Arbitrum. Token transfers are not used (a spam airdrop would otherwise become the "first funder"). A sender equal to the address itself is skipped. Funding that arrives through internal transactions (contract or batch withdrawals, Arbitrum L1-to-L2 deposits) is not in the `/transactions` list, so "first funder" means the first direct sender and may differ from Nansen's; the README says so (Task 6).
- Nansen is read-only history after this stage: saved readings, the 9 featured entries and the 307 archive entries keep their `source: 'nansen'`, their `all-chains` wording, their "Data from Nansen" section and their "Powered by Nansen API" credit. Types and renderers for them stay; clients, keys, budget wiring and fetchers go.
- Keep the Durable Object class `NansenBudget` and its binding in `wrangler.toml` under their current names (deleting a class needs a migration); the check path no longer reserves from it. `/api/ledger` serves the static September archive only.
- The explorer key is a Worker secret `BLOCKSCOUT_API_KEY`, optional. It is sent only in the `Authorization` header, never in a URL, a log line, a note or a test snapshot.

## Prerequisites owned by the owner (not blocking Tasks 1-5; blocking the release)

1. Register at https://dev.blockscout.com (free, no card), read the terms shown at sign-up, and tell the builder whether they say anything about displaying, storing (the site keeps dated readings) or redistributing data. Until a free key exists, Arbitrum funding links cannot be read (the public Arbitrum host is challenged), every funder search is `partial`, and a short that needs one reads Unknown instead of Bet. This is safe and honest, but it makes "Looks like a bet" unreachable for most shorts.
2. At deploy time: `npx wrangler secret put BLOCKSCOUT_API_KEY` (the owner types it; the builder never sees it). For a local live smoke with the key, put it in `.dev.vars` or the shell, never in a tracked file.

## Review Focus

- The explorer answering `200` with an HTML challenge page, a `403`, `402` (no key), `429` or an `items` that is not a list must count as that chain not read (coverage `partial` or `missing`), never as "no funder found". Only a `200` with a valid empty `items` list means "nothing came in". Test in Task 2.
- A first inbound transaction with value zero (a contract call) must be skipped, and a first page with no value-bearing inbound transaction but a `next_page_params` must read as incomplete, not as "no funder". Test in Task 2.
- `portfolio` answering with a missing `perpMonth`, a one-point history, or a non-numeric value must read as PnL unavailable (a note), never as a PnL of zero, and never fail the check. Test in Task 1.
- A saved reading whose `pnl` has the old Nansen shape (no `basis`) must still render exactly as before. Test in Task 1.
- Attribution for a mixed history: a new reading must not credit Nansen, and an old reading must keep crediting it, on all four surfaces (publisher DTO and embed, share text, downloaded card, link-preview picture). Test in Task 5.
